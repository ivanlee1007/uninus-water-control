Base P2 on P1 commit `1626196cc43b24e337145cf6f11020d78da698ce`; P2 PR targets the P1 feature branch. No merge, release, HACS listing, or connection to Jingan.

**Goal:** 使用者在 HA Dashboard 新增一張補水總覽後，能看到原生標題與各桶原生 Tile；新增、移除、改名或更新液位後畫面可自行同步，不需重寫 Dashboard YAML。

**Architecture:** Core 原生液位實體附最小的布局資料。卡片只讀 HA 傳入的 `hass.states`，不建立需認證的自訂 websocket、另存 inventory 或直接操作 switches。HA 2025.12.0 隨附前端的原生 Grid 用固定 `columns`，Sections 本身無法將整合清單轉成依區內實寬自動換列的動態子卡，所以只用一個輕量 custom card 承擔分組、調度原生卡片和 CSS grid。原生 Tile 持有讀值、可用性、More info 和相關歷史呈現。

## Frozen contract

- In `TankLevel.extra_state_attributes`, attribute `uninus_water_dashboard` is `{version: 1, zone: {id: <32 lowercase hex stable zone UUID>, name: <str>, index: <zero-based int>}, tank: {id: <32 lowercase hex stable tank UUID>, name: <str>, index: <zero-based int within zone>}}`. Use inventory order; names are display only; collection must survive unavailable readings. Only dashboard-safe attributes: no bound source IDs, switch IDs, registry IDs for other entities, switch values or policy fields. Actual tile entity ID is the key of the readable projection in `hass.states`, not a field in the attribute.
- Register a single exact static module URL `/uninus_water_control/dashboard.js` in `async_setup` if HTTP is initialized; `after_dependencies: ["http"]` to order normal HA startup without forcing HTTP (headless/Core fixtures still work). Document manual one-time module resource registration in HA. Never alter Lovelace storage/dashboards automatically. Static file is `custom_components/uninus_water_control/dashboard.js`.
- Frontend element `uninus-water-dashboard`, YAML `type: custom:uninus-water-dashboard`. Native `heading` (`zone.name`) + `tile` (`tank.name`, owned projection ID; tile/icon `more-info` with no generated service action or features). Can start with no valid data; use localized zh-Hant and English empty/loading/unavailable bridge states and stable re-render/focus. Native Tile handles sourced value, invalid/unavailable reading, and localization. Do not duplicate readout or rendering of native tile controls. Parent card provides layout only, observables for testing can be stable class / `data-zone-id` / `data-tank-id` host containers. Use HA provided `window.loadCardHelpers()` and `helpers.createCardElement(...)` with scoped loading/failure handling. Exact default names and arbitrary names must never use HTML interpolation. Cards keyed by opaque IDs; unaffected node identity and focus survive telemetry/equivalent config, name/order and inventory changes. Handle stale async module readiness or disconnected/recreated nodes. Guard registration/idempotence. No `callService`, custom API, persistent client writes or polling. Strictly filter malformed or inconsistent metadata; never derive raw output from entity names. HA dashboard sizing helper methods as appropriate.
- Layout uses measured component/container width, not viewport: CSS zone auto-fit around 340–360 px and per-zone auto-fit around 155–168 px subject to actual native tile sizing. Preserve narrow stacked / supported wide side-by-side zones. Support 1, 2, 3, 4+ tiles per row and incomplete last row with no horizontal overflow; tests measure rectangles, including fixed viewport/narrowed container. Do not force 2×2 on exactly four items. Theme by native style variables; test native light and dark if possible without need for a new custom theme.
